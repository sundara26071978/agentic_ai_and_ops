1. First understand the normal agent

Suppose we have this tool:

from langchain.tools import tool

@tool
def get_account_balance(account_id: str) -> str:
    """Get the current account balance from the banking system."""
    
    # Real production implementation
    return f"Account {account_id}: $125,000"

Normally:

User
 │
 │ "What is the balance of account A123?"
 ▼
Agent / LLM
 │
 │ decides:
 │ call get_account_balance("A123")
 ▼
Real Tool
 │
 │ executes Python/API/database
 ▼
Banking System
 │
 ▼
$125,000
 │
 ▼
Agent
 │
 ▼
User

With LLMToolEmulator:

User
 │
 ▼
Agent / LLM
 │
 │ decides:
 │ get_account_balance("A123")
 ▼
LLMToolEmulator
 │
 │ DON'T execute real tool
 │
 │ Ask another LLM:
 │ "Pretend you are get_account_balance"
 ▼
Emulator LLM
 │
 ▼
"Account A123: $125,000"
 │
 ▼
Agent
 │
 ▼
User

The real function is never executed.

That's the core idea.

2. Why is this useful?

The three use cases you listed are actually three progressively more advanced testing strategies.

Use case	What you're testing
1. Test agent behavior without real tools	Agent reasoning/orchestration
2. External tool unavailable/expensive	Agent development
3. Prototype workflow before tools exist	Architecture/workflow

Let's go through each with a practical program.

3. Use case #1 — Test agent behavior without executing real tools

Imagine you have:

@tool
def get_trade_status(trade_id: str) -> str:
    """Get the current status of a securities trade."""
    
    print("🔥 REAL TOOL EXECUTED!")
    
    # Expensive database/API call
    return "MATCHED"

You want to test:

Does my agent correctly decide when to call get_trade_status?

But you don't want to actually call the trade system.

Use:

from langchain.agents import create_agent
from langchain.agents.middleware import LLMToolEmulator

agent = create_agent(
    model="openai:gpt-5.6",
    tools=[get_trade_status],
    middleware=[
        LLMToolEmulator(
            tools=["get_trade_status"],
            model="openai:gpt-5-mini",
        )
    ],
)

Now invoke:

result = agent.invoke({
    "messages": [
        {
            "role": "user",
            "content": "What is the status of trade TRD12345?"
        }
    ]
})

The flow becomes:

                  User
                   │
                   ▼
              GPT-5.6
                   │
                   │ Tool call
                   ▼
        get_trade_status
                   │
                   ▼
       ┌────────────────────┐
       │ LLMToolEmulator    │
       └─────────┬──────────┘
                 │
                 │ intercept
                 ▼
             GPT-5-mini
                 │
                 │ simulated response
                 ▼
          "Trade TRD12345
             is MATCHED"
                 │
                 ▼
              GPT-5.6
                 │
                 ▼
          Final response

Notice:

print("🔥 REAL TOOL EXECUTED!")

will not execute.

That's because the middleware intercepts the tool call and returns a ToolMessage generated by the emulator LLM instead of invoking the actual handler.

5. Use case #2 — External tool is unavailable or expensive

This is where the emulator becomes very useful in development.

Imagine your real tool is:

@tool
def query_reference_data(
    isin: str
) -> str:
    """Query the enterprise security reference data system."""

    # REST API
    # authentication
    # network
    # database
    # etc.

    return call_reference_data_api(isin)

You don't have access to the reference-data system on your laptop.

Without emulator:

Agent
  │
  ▼
query_reference_data
  │
  ▼
❌ API unavailable

With emulator:

Agent
  │
  ▼
query_reference_data
  │
  ▼
LLMToolEmulator
  │
  ▼
LLM
  │
  ▼
Simulated security information

You can therefore develop your agent logic before the backend is ready.

6. Example — Securities reference data

Let's create:

@tool
def get_security_reference(isin: str) -> str:
    """Retrieve security reference information including currency,
    settlement cycle and asset class."""

    print("🔥 REAL REFERENCE DATA SYSTEM CALLED!")

    return """
    ISIN: US0378331005
    Currency: USD
    Asset Class: Equity
    Settlement Cycle: T+1
    """

Then:

agent = create_agent(
    model="openai:gpt-5.6",
    tools=[get_security_reference],
    middleware=[
        LLMToolEmulator(
            tools=["get_security_reference"],
            model="openai:gpt-5-mini",
        )
    ],
)

Ask:

result = agent.invoke({
    "messages": [
        {
            "role": "user",
            "content": (
                "Retrieve the security information for "
                "ISIN US0378331005 and tell me the settlement cycle."
            )
        }
    ]
})

The emulator receives information such as:

Tool:
get_security_reference

Description:
Retrieve security reference information including
currency, settlement cycle and asset class.

Arguments:
{
    "isin": "US0378331005"
}

and the emulator LLM generates a plausible tool response.

The implementation itself constructs a prompt containing the tool name, description, arguments and an instruction to generate a realistic response.

7. But be careful!

This is extremely important.

The emulator response is:

plausible

It is not authoritative.

For example, the emulator might produce:

ISIN: US0378331005
Currency: USD
Asset Class: Equity
Settlement: T+1

But you should never interpret that as real reference data.

Therefore:

LLMToolEmulator
        │
        ├── GOOD for:
        │    Agent testing
        │    Workflow testing
        │    Prototyping
        │    Development
        │
        └── BAD for:
             Production decisions
             Regulatory decisions
             Actual trade execution
             Real settlement
             Financial truth
8. Use case #3 — Prototype the workflow before implementing tools

This is perhaps the most interesting use case for your work.

Imagine you want to build:

Trade Prematching Agent

You haven't implemented any backend tools yet.

Your future architecture might be:

                    Trade Prematching Agent
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
       Trade Details    Counterparty     SSI Lookup
          Tool             Tool             Tool
              │              │              │
              ▼              ▼              ▼
          Database          API          Reference DB

But today you only have the agent.

You can define placeholder tools:

@tool
def get_trade_details(trade_id: str) -> str:
    """Retrieve trade details."""
    raise NotImplementedError


@tool
def get_counterparty_details(counterparty: str) -> str:
    """Retrieve counterparty information."""
    raise NotImplementedError


@tool
def get_settlement_instruction(
    counterparty: str,
    security: str
) -> str:
    """Retrieve settlement instructions."""
    raise NotImplementedError

Normally these would immediately fail.

Instead:

agent = create_agent(
    model="openai:gpt-5.6",

    tools=[
        get_trade_details,
        get_counterparty_details,
        get_settlement_instruction,
    ],

    middleware=[
        LLMToolEmulator(
            model="openai:gpt-5-mini"
        )
    ],
)

Because:

tools=None

means all tools are emulated.

Now you can prototype the entire workflow.

10. Selective emulation — very important

You don't have to emulate everything.

Suppose you have:

Tool A → database
Tool B → REST API
Tool C → local calculation

You might want:

A → emulator
B → emulator
C → REAL

Do:

LLMToolEmulator(
    tools=[
        "database_tool",
        "reference_data_tool"
    ],
    model="openai:gpt-5-mini",
)

Then:

database_tool
      │
      ▼
   EMULATED


reference_data_tool
      │
      ▼
   EMULATED


calculate_match_score
      │
      ▼
     REAL

This selective behavior is explicitly supported by the current API. tools=None means all tools; tools=[] means none; specifying names or BaseTool instances limits emulation to those tools.

14. One conceptual distinction to remember

Don't confuse:

Tool mocking
get_trade_status()
       ↓
"MOCKED RESPONSE"

with:

LLM Tool Emulator
get_trade_status()
       ↓
LLM
       ↓
"REALISTIC RESPONSE"

A traditional mock usually gives you a deterministic predefined response:

return "MATCHED"

LLMToolEmulator generates the response dynamically based on:

Tool name
+
Tool description
+
Tool arguments
+
LLM

The current implementation explicitly builds that emulator prompt and returns its output as a ToolMessage.

That makes it much more convenient for prototyping, but also less deterministic than a conventional mock.
